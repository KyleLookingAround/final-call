# Brief: Faster CI, second half: only the touched check groups on drafts

Runbook experiment [B]'s second half (`docs/ROADMAP.md`). The first half (cached Chromium, #46) merged; its look back in `docs/LESSONS.md` found the cache alone saves little.

## Goal and what it may touch

- One PR on `feature/ci-touched` from `main`: on a **draft** PR, the Checks workflow runs only the check groups `tools/graph.mjs` says the PR's changed files touch (plus `brief` and `graph`, which are cheap, and `sim` as a floor); on a PR marked ready for review, and on `main`, it runs everything as today. A new script (for example `tools/touched.mjs`) turns `git diff --name-only origin/main...HEAD` into the list of groups, falling back to every group for anything it can't map (`tools/build.mjs`, `src/shell.html`, `package*.json`, the workflows themselves). Marking a PR ready must re-run the full Checks (`ready_for_review` in `on.pull_request.types`).
- Merge safety: a draft's partial run must never be the run a merge relies on. Say in the PR how that holds (a PR can't be merged while draft; the full run fires on ready).
- Measure it: time-to-green of a draft that touches one check group, against a full run, from this PR's own runs; put the numbers in `docs/LESSONS.md`. If `install-deps` still dominates, say so and name the next step (caching the `apt` packages) without doing it.
- Update the `steward` and `feature` playbooks with one line each: open PRs as drafts while iterating, mark ready before merging.
- It may touch: `.github/workflows/checks.yml`, a new script in `tools/`, `tools/graph.mjs` only if it needs a small export to map files to groups, `docs/SYSTEMS.md` (a short paragraph under the checks), the project notes' Build and test section, `.claude/skills/steward/SKILL.md`, `.claude/skills/feature/SKILL.md`, `docs/ROADMAP.md`, `docs/LESSONS.md`, and this brief as `docs/briefs/ci-touched.md`. Not `tools/check.mjs` or `tools/build.mjs` (the terminal-place checks session is changing both now): run several groups by calling `npm run check -- <group>` once per group in the workflow, or ask in the PR if that proves too slow.
