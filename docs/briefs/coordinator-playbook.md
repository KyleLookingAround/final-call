# Brief: A coordinator playbook

The coordinator's brief for a small runbook change: write down how a coordinator runs the other sessions, from what the coordinator of 27 Sep 2026 learned. No game code.

## Goal and what it may touch

- A `coordinator` playbook, `.claude/skills/coordinator/SKILL.md`, in the same shape as the others (front matter with `name` and `description`, then short checkable lists). Branch `feature/coordinator-playbook` from `main`, one PR.
- It covers, in this order:
  1. **Starting fresh.** A coordinator starts fresh for each feature, from a brief. When it takes over, it retires the old one: check `list_triggers` has no Routine bound to it, then `archive_session`. The coordinator retired on 27 Sep had cost $176 and used 642k of context over 25 hours; the look back records it.
  2. **The sweep**, at each check-in: `list_sessions` (mine); for each live Final Call session, `get_session`'s `status_bucket`, `post_turn_summary.status_detail`, `usage.cost_usd` against its brief's estimate, `context_usage.used_tokens`, and `rate_limit_info`; `list_triggers` for booked check-ins; open PRs with their check runs and mergeability; open `needs-owner` issues.
  3. **Before a session merges,** read its PR's title and description for attribution (a "Generated by" line got into #39's), and look for lines the change makes wrong outside its diff: the README, code comments, the project notes (#39 left the README saying saves went to a claude.ai account).
  4. **Talking to a session.** `ListAgents` and `SendMessage` don't reach idle cloud sessions. Use `create_trigger` with `persistent_session_id` and `run_once_at` a minute or two ahead: it arrives as a user turn. `fire_trigger` on a session's own one-shot check-in brings it forward. Once it answered "internal error" yet did fire, and the one-shot was then gone, so check `get_session` (status running) before firing again. Never push to another session's branch: ask it. A PR description can be fixed directly.
  5. **How many at once.** At most three sessions on the default model, started just after a limit resets. Small changes and routine jobs (look backs, save fixtures, doc moves, screenshot reviews) go to the cheaper model (`create_session` with `model: "claude-sonnet-5"`). With `rate_limit_info.status` at `allowed_warning`, add nothing beyond the plan. At "rejected" or on overage, book a `send_later` for a minute after `resetsAt` and end the turn.
  6. **Starting a session.** Write its brief from `docs/briefs/TEMPLATE.md`, run `node tools/brief.mjs` on it, then `create_session` with `source_url`, `source_revision: "main"`, `outcome_branch: "feature/<name>"`, a title, a `final-call:<feature>` tag and the model. The first message is the brief, with one line asking the session to save it as `docs/briefs/<name>.md` in its PR.
  7. **One item per session.** When a session's item merges, it stops. New work goes to a fresh session with its own brief, never into a long conversation: #39 went into a finished session already at 470k of context.
  8. **One check-in.** The coordinator keeps a single `send_later`; parts don't book their own. Between check-ins, PR events and the check-in wake it, not polling.
- Also, each in a line or two: a pointer to the new playbook from the `feature` playbook's "Keep the coordinator light"; the playbook list in the project notes (one line); a line under "The runbook" in `docs/ROADMAP.md`; the look back described under "Who merges and when".
- It may touch: `.claude/skills/coordinator/SKILL.md` (new), `.claude/skills/feature/SKILL.md` (that one pointer), the project notes (that one line), `docs/ROADMAP.md`, `docs/LESSONS.md`, and this brief as `docs/briefs/coordinator-playbook.md`. Nothing in `src/game/` or `tools/`.

## When to stop and ask

- Only for something irreversible or outside this brief.
- Otherwise, if it truly needs the owner: open an issue labelled `needs-owner` with the question and the option it will take by default, carry on with other work, look at the issue at each stopping point, and take the default after 12 hours with no answer. Say so in the PR.
- Where it's merely unclear, take the safer option (easier to undo, or changing the game less) and say so in the PR.
