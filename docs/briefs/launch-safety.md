# Brief: Launch safety: main is green, a release cadence, and launch-day triage

Three small process changes for launch week (the owner starts sharing the game on 28 Sep 2026). Workflows and docs; no game code.

## Goal and what it may touch

- One PR on `feature/launch-safety` from `main`, with:
  1. **Main is green.** Nothing tests `main` today: `pages.yml` builds and deploys on every push, and PRs are only tested on their own heads, so two PRs each green and merged minutes apart can combine into a broken live game. Add a job to `pages.yml` (or a `main.yml` that `pages.yml` waits on) that runs `npm ci` and `npm run check` on `main` before the deploy step, with the same Playwright cache as `checks.yml`. On failure: no deploy, and open (or update in place, one issue, marker comment) an issue titled "main is red" labelled `bug` naming the failing check and the merge that broke it. Keep the docs-only skip `pages.yml` has today (a push that doesn't change the page's sources needs neither check nor deploy). Note the cost: about 8 minutes per publish.
  2. **A release cadence** (the `release` playbook, a new short section): during a launch week, one release a day at most, hotfixes excepted; no new systems for 48 hours after a launch post, sessions fix what players report and polish instead. Reason: the update toast comes back hourly on "Later", so five versions a day nags the players we want to keep.
  3. **Launch-day triage** (`docs/briefs/launch-triage.md`, and a line in the `coordinator` playbook next to the tidy and the watchdog): the brief-as-prompt for a Routine that fires every two hours into a fresh session on the cheaper model. Its job: read GitHub issues opened since its last firing (the in-game Send feedback link opens them with version, level, layout, day and screen size filled in), reproduce each on the matching `tools/saves/` fixture where it can, label it (`bug`, `balance`, `idea`, `question`), open one fix PR per bug that is small and clear (the `feature` and `steward` playbooks, squash-merge when green), and write one summary comment on a single "Launch-day triage" issue (updated in place) for the owner: what came in, what was fixed, what needs them. Write it in the shape of `docs/briefs/lessons-tidy.md` and `docs/briefs/watchdog.md`; the coordinator creates the Routine from the committed text and puts its id in the playbook in a follow-up. Include a cost line (about $3 a firing when there are issues, under $0.50 when there aren't) and a stop line (no fix PRs for anything that changes rules or baselines: those get labelled and summarised).
  4. **Merge queue, proposed** (`docs/roadmap.d/2026-09-28-merge-queue.md`, `Section: next`): a roadmap item proposing GitHub's merge queue on `main` (a ruleset, the owner's to set) as the replacement for the Catch up workflow's merge-and-dispatch dance and for item 1's race: it tests each PR against the combined head before merging, in order. Say what changes for sessions (they add to the queue instead of merging) and that it's for after launch week.
  5. This brief as `docs/briefs/launch-safety.md`, and a short look back.
- Files it may touch: `.github/workflows/pages.yml`, a new `.github/workflows/main.yml` if you go that way, `.claude/skills/release/SKILL.md`, `.claude/skills/coordinator/SKILL.md` (one line; another session is editing §5 and adding §11 tonight, so add your line at the end and merge `main` before pushing), `docs/briefs/launch-triage.md`, `docs/briefs/launch-safety.md`, `docs/roadmap.d/`, `docs/lessons/`, and `docs/SYSTEMS.md`'s workflow list if it names the workflows.
