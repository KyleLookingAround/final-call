# A page size budget check (#140) · 28 Sep 2026

- **Numbers:** estimate $3; about $5.50 by the time this was written (past twice the estimate once the fresh review and catching up with `main` twice are counted in; the check itself and its docs were done inside the first hour). About 21% of the session's context used. Started 15:44 UTC, PR opened ready for review (not draft) at 16:06, two pushes after opening plus one from the Catch-up workflow, no red CI, two merges from `main` by hand and one by the Catch-up workflow (`main` moved twice while the PR was open, once for #134's auto-merge switch and once for #141's roadmap tidy).
- **Went well:** the check reads the `dist/index.html` the build already made and does no browser work, matching the brief's CI-time budget exactly; `tools/touched.mjs`'s existing `tools/checks/[\w-]+\.mjs` pattern picked up the new group with no change needed. Measuring the real page's structure first (`<style>`/`<script>`/`data:` boundaries) before writing the check kept the budget's breakdown accurate rather than guessed.
- **Lessons:**
  - Going straight from writing the code to opening the PR skipped the brief's required fresh review; it had to be run after the PR was already open, adding a round of description edits. → Run the fresh review before `create_pull_request`, not after, even for a change that feels too small to need one.
  - The review's own use of a plain `git diff origin/main..HEAD` (two dots) flagged an "unintended revert" of #134 that wasn't real: two-dot diff shows a stale local branch's missing upstream commits as if the PR removed them. Three-dot (`git diff origin/main...HEAD`) and GitHub's own PR comparison, which both use the merge base, showed the true 7-file diff throughout. → Tell a reviewer to use the three-dot form (or read the PR's own file list) when checking a PR's real diff against a moving base.
  - `main` moved twice during a 25-minute PR (a Publishing-process change in #134, then a roadmap tidy in #141): the Catch-up workflow's own push landed between this session's two merges, so the second merge had to reconcile the workflow's commit as well as `main` itself. Both were clean, but it took an extra fetch-merge-push round. → Expected, not a problem; noted here only because the "two merges" count the playbook asks for was genuinely two-by-hand-plus-one-by-workflow, not one.
  - CLAUDE.md's Publishing section changed mid-session (from "the session squash-merges" to auto-merge plus a ruleset) via the #134 merge that landed in this same PR's history; the steward playbook had already been updated to match. → Re-read the project notes and steward playbook after any merge from `main`, not just at session start, since a sibling session's process change can land under you.
