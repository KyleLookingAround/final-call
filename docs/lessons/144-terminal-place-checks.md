- **How [D] was measured:** each part's PR records (a) game-code bugs a pre-written check caught before it opened, (b) bugs found after, (c) pre-written checks it had to fix. The baseline was the terminal's 0.6 late bugs a part; [D] stays if (b) is at most 0.3 a part. → Recorded in each part's lesson (`162-terminal-place-floors.md` has the last).
- **Lessons:**
  - #90's plan missed that `Object.assign(SIMX,{get X(){…}})` already flattens a getter before the hook runs; the `rules` check, written first, showed it at once. → The test page keeps each property as written (`tools/build.mjs`).
  - Budget a check's run time before writing it: #90's first draft took 33 s, mostly opening pages, so checks whose play takes seconds wait until their code exists (`TP_ALL=1` plays them now) and the rest share pages; #144 timed one level 9 game day first (about 9 s at 0.1-minute steps) and used fine steps only around the events.
  - **A pre-written check must be able to fail, and to pass for the right reason.** #90's review found a check that could never fail (toasts don't happen in the headless sim, so "the crowd is the only sign" counted nothing) and six more that would have misled a part; #144's review found a runner who never changed floor, "0 up in rain" with nobody up in the dry, and one sampling floors once a frame at 8× that could fail a correct build. → Every "none of X" pass mark needs "and X could happen" in the same check, and the review stays (`feature` playbook, step 4).
  - A flight's `std` doesn't say when its gate is called: boarding opens, and the gate is called, hours before `std` (#144 lost two rounds on this). → A check that needs a gate call reads `callAt(F)` or causes the call (`TP.hurry`), and never reasons from `std`.
