# Release F2, goals and levels that lead (#149) · 28 Sep 2026

- **Numbers:** estimate $6; about $14.50 by the time the PR was open and merging (over twice the estimate). One session, five commits (two of substance, three from merging `main` in twice as R1, P1 and P2 landed underneath). No bot run needed: the changed code isn't reachable from the bot's play (goals are checked in the frame loop, and the curfew stays off by default). The five-hour rate limit stopped the turn once for about an hour; the coordinator's wake-up picked it back up.
- **Went well:**
  - Reading the audit's per-row "Files" column at face value nearly caused two scope breaks. Actually tracing every dynamic call site of `has('...')` (not just the literal ones a first grep finds) before touching its fallback caught a real, reproducible crash (`modeLocked('bus', ...)`) in a file this batch may not touch, and found that dozens of legitimately unlocked-from-the-start items (the starter plane, base upgrades, bus lines) relied on the old "unknown key returns true" behaviour. A blanket "return false for unknown key", as the row's fix literally said, would have broken the base game. `keyExists()`, checking a key against its real category registry, fixes the actual bug (a typo) without the regression, and stays inside the one allowed file.
  - The `migrate` check (recorded golden hashes for every save fixture) caught a real correctness bug the new `rules` checks didn't: making a level goal's `p()` track the live least-met requirement, instead of `G.level`, meant an already-reached level's goal could read as "not met" again if a requirement (rating) later drifted, or during a pre-Masterplan save's one-time migration backfill. Fixed by keeping `p()` at `[1,1]` once `G.level>=n`. Running the full `npm run check` before opening the PR, not just the groups the diff touches, is what surfaced this.
- **Lessons:**
  - **A row's "Files" column names where the fix's main logic lives, not everywhere the fix's description implies a change.** Row 8 said "say so on the policy card" but named only `09-construction-levels-days.js`; row 28 said "hide counts until the tab's first visit" but named only the same file. Both extra asks needed `01-constants.js`/`03-state.js`/`15-panel.js`, owned by other batches. → A fix session should read a row's prose fix as the target and its Files column as a lower bound, not an exact list; where they conflict, the brief's own file-scope rule wins, and the gap goes in the PR (done here) rather than being implemented in someone else's file.
  - **Running two `npm run build` calls concurrently with a background `npm run check` run corrupted that run's results** (it read a `build/test.html` that changed mid-run). Lost about 10 minutes re-running clean. → When a check run is going in the background, don't build again until it's done; if you must, kill and restart the check run rather than trust its output.
  - **A change that "shouldn't affect other systems" still deserves the full check suite before opening,** not just the groups `node tools/graph.mjs` names for the touched files: `migrate` isn't listed against `02-masterplan.js`, but it caught the one real bug this session shipped.
  - **Most of the overrun was three full `npm run check` runs (about 3–4 minutes each in this sandbox) around two `main`-catch-up merges**, on top of the one that caught the row 6 bug. Each merge (R1, then P1 landing right behind it) needed a fresh full run to trust the result, since a partial run wouldn't have caught a bad interaction with the newly merged code. → For a small batch like this, a full run after the *last* expected `main` movement, not after each one, would have been enough once the targeted groups (the ones the diff and the merge together touch) stayed green; that's what the second merge in this PR actually used, and it was faster.
