# Release fix batches: #149 F2 goals, #150 P1 first level-up, #158 R1 saves, #159 P2 moments · 28 Sep 2026

Batches from the release audit, each in its own files ("no other game file: other batches own them").

- **Numbers:** #149 estimate $6, about $14.50 by merging (five commits, two of substance, the rest merging `main` as R1, P1 and P2 landed); the five-hour limit stopped it once for about an hour. #150 estimate $6, about $6.9; opened 20:25; UI only, no bot run. #158 estimate $10, cost not reported; two files of game code, one check group, one full `npm run check` (358/358). #159 estimate $5, about $9; opened 20:59; two full check runs and a fresh-review round. None needed a bot run of its own, apart from #158's `PLAY` question below.
- **Went well:**
  - The brief's file restriction held under pressure (#159): two of the audit's row fixes lived outside the batch's files, and the narrower fix was taken each time, with the gap written in `docs/systems/sound.md` and the check file.
  - #158 wrote the checks first and ran them on a build of `main`, showing every row failing with the audit's numbers (one stash, a build, one group run). Looking at the warnings as screenshots caught the guided start covering the broken-save warning on a phone, which the checks couldn't see because `open()` clears the boot's toasts.
  - #149 traced every dynamic call site of `has('...')` before touching its fallback, and found a reproducible crash (`modeLocked('bus', ...)`) and dozens of legitimately unlocked-from-the-start items that relied on "unknown key returns true". `keyExists()` fixes the typo without the regression. The `migrate` check (golden hashes for every fixture) then caught a correctness bug the new `rules` checks didn't: a goal's `p()` tracking the live requirement made an already-reached level read "not met" again when the rating drifted.
  - #150 needed one line at each end of the queue (`lvlUp` refuses the card during the tour, `lvlTick` waits for `G.tour.done`, `tourNext` calls `lvlTick`), with no new saved field.
- **Lessons:**
  - **A row's "Files" column is a lower bound, not the list.** #149's rows 8 and 28 named one file but their prose needed `01-constants.js`, `03-state.js` and `15-panel.js`, owned by other batches. → Read the prose as the target; where it conflicts with the brief's file rule, the rule wins and the gap goes in the PR (`feature` playbook, "Working while the owner is away").
  - **A fix that can't reach its real call site invites a workaround that reaches further than intended.** #159's first pass debounced `kaching()` globally, which would have silenced a purchase's chime whenever it landed within 600 ms of an on-time departure's (`settle()`, called continuously in play): a worse regression than the complaint. The review caught it. → Before adding state to a function you're allowed to touch, check what else calls it; a shared primitive is the wrong place for a fix meant for one caller.
  - **A check for "N happen once, not once each" needs a scenario where N is more than one** (#159: two stamps qualifying together, asserting the exact oscillator count); a check with two call sites for one effect needs both exercised (#150: dropping `lvlTick()` from the Skip-tour branch passed every check because only `tourNext` ended the tour, confirmed by reverting the fix and watching the new test fail). Two rendered rows sharing one `data-lvgo="plan"` value over-counted a check that counted by it: scope to one section's markup (#150). When a guard combines conditions, ask what each one gates before changing any of them.
  - **A reload saves first.** #158's repeated-load check passed on `main` because the reload's `visibilitychange` save wrote `savedAt` as now. → A check that reloads to test time away blocks the unloading page's save (as `saves` now does), and every new check is shown failing on `main` before a pass is trusted. The audit's row 2 said "revenue" while the old bonus paid net (`G.rate`), and its size (up to three hours away pays about 2.6 game days' profit) is a balance question left for the owner.
  - **"The bot never loads or saves" was wrong** (#158): it boots the page, and the boot saves, so every run carried the new `G.ver`, and `PLAY` differed on all three seeds; comparing with the moved `main` gave a false alarm. → `PLAY` leaves out `G.ver` (`tools/run-bot.mjs`); a PR that adds a saved field runs the bot against its base commit before claiming `PLAY` is identical.
  - **Run the full check before opening, not only the groups the diff touches.** `migrate` isn't listed against `02-masterplan.js` yet caught #149's one real bug. But after `main`'s last expected movement one full run is enough; targeted groups after each earlier merge (#149 ran four full runs at 3–4 minutes each). Don't `npm run build` while a background check runs: a `build/test.html` that changes mid-run corrupts it (#149, about 10 minutes lost).
  - The full check took 15–20 minutes, not "1–2", in #159's sandbox, and Node buffers stdout to a file until exit, so it looked stalled (see `156-systems-refactors.md`, machine hygiene). → Budget 15–20 minutes, and check `ps` for the process rather than a stdout file that won't fill.
