- **Lessons:**
  - A fix that can't reach its real call site invites a workaround that reaches further than intended. Asked to make "several goals completing together ring the till once" without touching `checkGoals()` (`15-panel.js`, off-limits), the first pass debounced `kaching()` itself globally — which also covers `settle()`'s on-time bonus (`08-stands.js`), a call site that runs continuously during real play and isn't `R.sim`-gated. That would have silenced a purchase's chime whenever it landed within 600ms of an unrelated on-time departure: a worse regression than the three-kachings complaint it was meant to fix. The fresh review (step 6 of the `feature` playbook) caught it before the PR opened. → When a fix's real location is out of scope, check what else shares the function you're allowed to touch before adding state to it; a shared primitive (`kaching()`, called from five places) is the wrong place for a fix that's only supposed to apply to one caller.
  - The first version of the chime-batching check only asserted "at least one chime plays", which would pass even if a regression made it chime once per item instead of once per batch. Constructing a scenario where two stamps (or two challenges) actually qualify together, then asserting the exact oscillator count, is what proves the batching claim rather than just the "not silent any more" claim. → A check for "N happen once, not once each" needs a scenario where N is genuinely more than one, not just a happy path where one item happens to complete.
  - The full `npm run check` (61 groups, mostly `page.waitForTimeout` real-time waits) took far longer than the "about 1–2 minutes" the project notes describe, in this sandbox — closer to 15–20 minutes each of the two times it ran. Node buffers stdout to a file until exit, so the output looked empty (and the process looked stalled, with very low cumulative CPU) well past the point it was actually still working through the wall-clock waits. → In a resource-constrained sandbox, treat a background `npm run check` as I/O-bound and budget 15–20 minutes before assuming it's stuck; check `ps` for the process still existing rather than reading a stdout file that won't fill until the process exits.
