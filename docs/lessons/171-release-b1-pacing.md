# Release B1, level pacing and payoffs (#171) · 29 Sep 2026

- **Numbers:** estimate $15; the session's cost wasn't reported (`usage` absent from `get_session`). Started 03:19 UTC, PR opened 04:45. About 50 bot runs of 1,200 hours (seeds 1–3 for `main`, each row alone, the variants of rows 18 and 20, row 21's ads runs and the final combination), run three to nine at a time from copies of the build in the scratchpad. One full check round locally; no helper agents.
- **Went well:**
  - Copying each variant's `build/` and `tools/` into its own folder and starting its three seeds there let the rows run side by side, with no rebuild racing a run in progress. A two-line status script that printed each run's `LVLAT`, `PLAY` and final fare made every comparison one command.
  - Tracing the first flight minute by minute (what each passenger was doing) found the stowing bottleneck in one run: everyone was at the gate half an hour before departure, and the aisle seated under one a minute.
  - `PLAY` identical across a change is a fast proof. It showed row 18 left the default untouched, and it showed row 20's first try did nothing at all.
- **Lessons:**
  - **The bot's fare is decided in the first morning.** It raises fares under a rating of 70 and lowers them only at 92, and a new airport starts at 60. So a slow first morning left seed 1 at 240% for 1,000 hours and stuck at City Airport. What looked like a pacing problem in the game was the bot's fare rule plus late first flights. → The bot now stops raising fares where the advisor's tips stop (120%), as a player following them would (the coordinator's addition to the brief), and the `balance` playbook says to read the snapshots' `fare` when one seed lags.
  - **An audit's constant can be dead.** `STAND` in `01-constants.js` is overwritten by each layout, so row 20's cheaper gate changed nothing. → A comment on `STAND` now says where gate prices live. Before tuning a constant, run one seed and check that `PLAY` changes.
  - **Guard checks that compare a seeded play with `main`** (`rules` passenger states, `weather-fx`, `daystats`) fail on any change that moves the dice on purpose. Re-record them with their `*_RECORD=1` variables, one group at a time: `npm run check -- a b` runs only group `a` (`tools/check.mjs` reads one argument).
  - **`scene` is noisier than its budget here.** `main` read 0.321–0.333× for Midfield desktop and this branch 0.32–0.374×, against a ±0.05 speed budget. Measure speed only on a quiet machine, and compare against `main` on the same machine, not against the audit's numbers.
  - **I misread a one-group run as three.** After re-recording, `npm run check -- rules weather-fx daystats` printed 27/27. That was `rules` alone, and for a few minutes I thought `weather-fx` had been flaky. Read the pass count against the group sizes.
