# #46 Runbook experiment [B], second half: only the touched check groups on drafts · 27 Sep 2026

- **Numbers:** estimate $5, about $19 by the time the PR was ready to merge (see "Lessons" below for why). PR #79 opened as a draft 17:21. Two real full runs, from this PR's own commits touching files `tools/touched.mjs` can't narrow (`.github/workflows/checks.yml`, then later `src/shell.html` from a `main` merge): 7m18s (`pull_request`, 17:22:04–17:29:22) and 7m8s (`workflow_dispatch`, 18:13:01–18:20:09) — 31s of fixed setup (checkout, `npm ci`, a Playwright cache hit, `install-deps`) then 6m40-ish for all 186 checks, both times. `tools/touched.mjs` correctly mapped both to "every group" on the first try.
- **Went well:** the fallback logic proved itself twice on this PR's own real runs without needing a special test — a workflow file and `src/shell.html` are exactly the cases the brief calls out, and `tools/touched.mjs` mapped both correctly. Local testing of `groupsFor()` across game-file-only, docs-only, mixed and unmappable file sets (during development, before any push) matched by hand in every case.
- **Lessons:**
  - The touched-only side had to be measured locally instead of live: `npm run check -- sim`, `-- graph` and `-- brief` (the floor every draft run keeps) together take about 4-5 seconds on this machine, each a fresh process and browser launch, same as the workflow's `for g in $groups; do npm run check -- "$g"; done` loop. Against the fixed 31s of setup, that means **`install-deps` (and the rest of the fixed setup) dominates a touched-only run** — the opposite of a full run, where 31s is a rounding error next to 6m43s. The next step, if this is worth chasing further, is caching the `apt` packages `install-deps` installs rather than only the Chromium binary the existing cache covers (not done here).
  - Two of this PR's `pull_request` `synchronize` pushes got no Checks run at all — no run, not even queued, 15+ minutes on each — while a manual `workflow_dispatch` on the same commits started within seconds both times (once needing one re-run after: a `news` check flake, unrelated to this PR's diff and already passing locally on that commit — several other sessions independently hit the identical flake the same day). GitHub runs no `pull_request` workflow at all while a PR's `mergeable_state` is `dirty`, and with roughly a dozen sessions writing the same shared lists that day, this branch was very likely conflicting against a fast-moving `main` at both of those moments without yet showing it. → Confirmed independently by several sessions the same day; #94's one-file-per-entry restructuring and its Catch up workflow (merged into `main` partway through this PR's own life, and merged into this branch in turn) are exactly the fix.
  - `main` moved seven times while this PR was open — the busiest day this repo had seen — each needing its own merge-in, so most of the cost overage was CI rounds and local `npm run check` runs repeated after each merge rather than the feature itself, which was small and worked first time. Confirms #94's own numbers rather than adding a new one.
  - Mid-PR, `main` gained exactly the fix this entry and several others called for (#94, one file per lesson/roadmap entry, joined lists, and a Catch up workflow that merges `main` into open PRs automatically) — merging it into this branch, already deep in its own merge-chasing, needed adapting this PR's `docs/LESSONS.md`, `docs/ROADMAP.md` and `CLAUDE.md` edits to the new file-per-entry shape rather than a plain merge. Worth knowing that a structural docs PR landing under an old-shaped PR costs one adaptation pass, not just a conflict to resolve.
