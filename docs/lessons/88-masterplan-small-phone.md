# #88 Masterplan on a small phone · 27 Sep 2026

- **Numbers:** estimate $5: well over by the merge (multiple rounds of `main` chasing), started 17:20, PR opened 17:46 (26 minutes, both commits already in when it opened). Six or more merges from `main` by hand before the Catch up workflow and `tools/join.mjs` landed partway through and took over the shared-doc conflicts.
- **Went well:** the brief's two `tools/graph.mjs` queries (`openPlan`, `TECH`) were enough to find both fixes without reading anything else first; `openPlan`'s `scrollIntoView` fix was a one-word change (`center` → `nearest`) once the audit's own measurement (`top:-79px`) explained why centring overshot.
- **Lessons:**
  - The fresh review before opening caught a real bug: `planUnlockLine` only listed aircraft/route/transport unlocks, so a recommended plan outside "Fleet and routes" showed *less* than an ordinary ready card, the opposite of the row's intent. Reusing the same `itemName` list the normal card already builds fixed it and was worth the review's cost.
  - `create_pull_request` appends a "Generated by" footer regardless of the project notes; the Description check fails on the very first run against it. Editing the description straight after opening re-runs it green with no push needed — expected friction, not a bug.
  - Merging `main` in silently broke row 6 again: `masterplan`'s own check caught it (`headTop` went from 86 to -5). A touch-target batch merged mid-PR grew `.chip` padding enough that scrolling the whole ready card into view (`block:'nearest'` on `.tnode.s-ready`) had to push the header off again. → Scroll target moved to the section's own heading (`[data-sec="ready"]`, a few lines tall), so the minimum scroll needed stays small regardless of how tall the list above it grows. Any fix that scrolls a variable-height target into view on a small screen should target the smallest anchor that proves the section is reachable, not the whole thing — only a check that measures actual pixels will catch a later regression.
  - Before the Catch up workflow existed, `main` moved five times by hand-merge count, each time conflicting only in shared docs (`docs/LESSONS.md`, then also `docs/SYSTEMS.md`, then `tools/build.mjs`'s old `SIMX` list) — never this PR's own files. Two of those pushes landed while the PR was still shown as conflicted, so GitHub queued no `pull_request`-triggered CI at all; `mergeable_state` itself lagged, and the one fully reliable signal was `merge_pull_request` refusing outright with a 405. Dispatching `checks.yml`/`balance.yml` by hand on the branch got a real signal each time.
  - Mid-PR, `main` landed the fix for exactly this (ADR-2026-09-27-fewer-clashes): lessons and per-system notes became one file per entry, joined by `tools/join.mjs`, and a Catch up workflow now merges `main` into open PRs itself. The in-flight hand-resolutions of `docs/LESSONS.md`/`docs/SYSTEMS.md` had to be redone as `git checkout --theirs` on those two files plus a new `docs/lessons/<pr>-*.md` entry and an edit to `docs/systems/levels-and-masterplan.md`, rather than a text merge. → Matches the ADR's own prediction; this entry is the first lesson filed under the new scheme for a PR that started before it existed.
  - `tools/build.mjs`'s `SIMX` list also stopped being a hand-maintained string somewhere in the same window: it now scans `tools/`, `tools/checks/` and `build/*.mjs` for `S.<name>`/`__sim.<name>` and exposes every matching top-level name automatically. A check file that already writes `S.recommendedTech(...)` needs nothing added anywhere else for that name to reach `window.__sim` — the old advice to "add it to the list in `tools/build.mjs`" no longer applies.
